comportement différent. La borne écrite couvre la quantification et laisse
dehors la dérivation, qui est le cas le plus fréquent dans un espace de nommage

muette ni vraie que `--compare` traite comme un fait. Déplacé du cas improbable
(« le voisin sert un modèle sans rapport ») au cas probable (« le voisin change

## 4. NON BLOQUANTE — le garde lit `docker-compose.yml`, **docker lit aussi l'override**

Le mandat demandait le **cinquième scénario**. Le voici, et il est mesuré.

### Ce que le garde neuf tient — et il tient beaucoup

| Forme | Ce que le garde fait |
| :--- | :--- |
| *témoin* — le fichier du dépôt | **20,0 s**, juste |
| service renommé | **rouge**, en nommant le service |
| healthcheck déplacé sous `deploy:` | **rouge**, en nommant la clé |
| **ancre YAML + `<<:` merge key** | **8,0 s — juste** |
| **ancre sur le healthcheck entier** | **8,0 s — juste** |
| **fragment `x-` non utilisé** | **20,0 s — juste**, il ne le lit pas |
| valeur interpolée `${HEALTH_INTERVAL:-8s}` | **rouge** |
| `extends:` vers un autre fichier | **rouge** |
| `healthcheck: {disable: true}` | **rouge** |
| clé dupliquée | **8,0 s — juste** (comme docker, la dernière) |
| `8S`, `-8s` | **rouge** |

Les ancres, les alias, le merge key et les fragments `x-` que le mandat nommait
sont **tous** correctement traités : `yaml.safe_load` les résout, et le garde lit
sous `services.agent-api.healthcheck` comme docker le fait. **Sur ces quatre-là,
il n'y a pas de cinquième scénario à trouver : il n'y en a pas.**

### Le cinquième est ailleurs — `docker-compose.override.yml`

Docker Compose charge **automatiquement** `docker-compose.override.yml` et le
fusionne. Le garde ne lit que `docker-compose.yml`.

```
A. sans override (témoin)   docker applique interval = 20s | le garde lit 20,0 s   → accord
B. avec override 8s         docker applique interval =  8s | le garde lit 20,0 s   → VERT ET FAUX
   rc(pytest tests/unit/) sous override = 0 — 870 passés
```

Le `docker compose config` ci-dessus ne démarre rien ; il a tourné dans l'arbre
de mutation isolé, l'override retiré ensuite, `porcelain` vide.

**Et le garde promet explicitement le contraire.** Sa propre docstring écrit :
*« porter le délai par requête à 7 s, ou **ramener l'intervalle du compose à 8 s**,
rougirait ici et nulle part ailleurs »*. Par le chemin que docker utilise
réellement, l'intervalle **est** ramené à 8 s et **rien ne rougit**. Le pire cas
de la sonde est 9,0 s : sous cet override, chaque battement empilerait une sonde
sur la précédente, sur le serveur partagé — le dommage exact que ce garde existe
pour empêcher.

C'est **le faux vert S4 du cahier des charges, réintroduit par un autre chemin** :
une modification parfaitement anodine, prise seule, suffit.

**Aucun override n'existe dans le dépôt aujourd'hui** — vérifié, `docker-compose.yml`
est le seul fichier compose. La trouvaille est donc prospective, comme S4 l'était.

## 5. Le critère d'appartenance à la signature — il ne juge que les cas pour lesquels il a été écrit

Le critère écrit : *« un champ entre si et seulement s'il est invariant pour un
moteur donné et varie quand le moteur change »*.

### La mesure de REPAR-19, rejouée

Deux lectures de `/v1/models` contre l'instance, **236 s d'écart**
(19:51:09 et 19:55:05 UTC) :

| champ | lecture 1 | lecture 2 | verdict |
| :--- | :--- | :--- | :--- |
| `id` | `google/gemma-4-E4B-it-qat-w4a16-ct` | identique | **STABLE** |
| `max_model_len` | 32768 | 32768 | **STABLE** |
| `created` | 1789501869 | 1789502105 | **CHANGE** |

**La mesure de REPAR-19 est confirmée** (elle annonçait 449 s d'écart, même
conclusion). Version `0.28.0`, **une seule entrée** au catalogue.

### Éprouvé sur les autres champs — et c'est là qu'il cède

| champ | invariant ? | varie ? | le critère dit | le code fait |
| :--- | :--- | :--- | :--- | :--- |
| `serveur`, `version`, `modele_servi`, `empreinte_du_modele` | oui | oui | ENTRE | **DANS** |
| `fenetre_servie` | oui | oui | ENTRE | **DANS** ✅ |
| `releve_le` | **non** | oui | SORT | **HORS** ✅ |
| **`endpoint`** | oui | oui | **ENTRE** | **HORS** ❌ |
| **`quantification`** | oui | oui | **ENTRE** | **HORS** ❌ |

Le critère tranche **exactement** les deux champs pour lesquels il a été écrit,
et **se trompe sur les deux autres** qu'il rencontre.

Le cas `endpoint` est le plus net : **le suivre produirait une régression.** Deux
campagnes contre le même moteur joint par deux formes d'URL — nom de service
docker d'un côté, hôte local de l'autre — signeraient `DIFFÉRENT` alors que le
moteur est le même. C'est précisément le défaut que la seconde moitié du critère
existe pour écarter, et le critère ne l'écarte pas.

Ce qui exclut réellement ces deux champs n'est pas écrit : `endpoint` désigne la
**voie d'accès**, pas le moteur ; `quantification` est **déjà portée** par
`empreinte_du_modele`. Il manque au critère une clause de redondance et une
clause d'identité. **Un critère qui ne juge que les cas pour lesquels on l'a
écrit n'est pas un critère** — mais le code qu'il justifie, lui, est juste.

*Contrôles* : la signature sait mordre (deux fenêtres → différentes ; deux noms →
différents) ; *témoin inerte* : un champ hors signature (`options`) ne la change pas.

## 6. Réserves

- **R-1 — le contrôle positif du critère porte sur l'horloge, pas sur la
  configuration.** `created` est **exactement l'heure de la requête** : mesuré
  1789502105 = `2026-09-15T19:55:05Z`, à la seconde près de l'heure machine. Il
  établit bien que la comparaison sait voir un changement — il est valide comme
  tel. Mais il ne peut rien établir sur la **première** moitié du critère : que
  `max_model_len` soit stable sur 236 s (ou 449 s) mesure un **non-événement**,
  pas une invariance. Ce qui l'établirait est un redémarrage du serveur avec un
  autre `--max-model-len` : **interdit ici**, et c'est dit au §7.
- **R-2 — `interval: 0s` fait rougir le garde à tort.** Docker traite `0s` comme
  « valeur par défaut » (30 s) ; le garde lit `0.0` et le budget rougit alors que
  la réalité est saine. C'est un **faux rouge**, pas un faux vert : le sens de
  l'échec protège, et cela vaut mieux que l'inverse. Relevé pour exactitude.
- **R-3 — `quantification` : la conséquence est aujourd'hui absorbée.** Ma
  première scène montrait deux quantifications signant `IDENTIQUE` — elle posait
  `empreinte_du_modele` à `None`. **Mesuré sur l'instance Ollama de ce poste :
  les 3 modèles servis portent tous un `digest`** (quantifications relevées :
  `F16`, `Q4_K_M`, `FP8`). Le cas ne se produit donc pas dans la configuration
  actuelle. Le défaut du **critère** (§5) reste ; sa conséquence pratique, non.
