## Méthode

Un garde n'est jamais jugé à sa lecture. Chaque mutation est appliquée au code,
les **deux états** sont montrés, la restauration est vérifiée par **empreinte
SHA-256** ET par `git status --porcelain` vide, et chaque sonde porte un
**contrôle positif** prouvant qu'elle atteint son cas. Le banc refuse de
mesurer si la mutation n'a **rien changé** (`assert s != avant`) et signale un
rouge obtenu sur un `NameError`.

Le `rc` relevé est celui de **`pytest`** (`PIPESTATUS[0]`), jamais celui d'un
`tail` ou d'un `echo` — piège payé deux fois par REPAR-12 et **trois fois par
moi** dans cet audit, §8.

# RÉSERVES

## R-1 — la propriété de B-3 repose sur une version d'AnyIO qui n'est épinglée nulle part

L'énoncé demandait, si la réponse dépend d'une version d'AnyIO, de dire
**laquelle et où elle est épinglée**. Mesuré :

| question | réponse |
|---|---|
| version qui porte la mesure | **anyio 4.15.1** |
| épinglée dans `requirements.txt` | **non** |
| épinglée dans `requirements-dev.txt` | **non** |
| épinglée dans `pyproject.toml` | **non** |
| dans `uv.lock` | **4.14.2** — une autre |
| ce que la CI installe | `pip install -r requirements.txt -r requirements-dev.txt` — **le lock n'est pas utilisé** |

`anyio` arrive en transitif par `fastapi`/`starlette`/`httpx`, et la résolution
libre a installé **4.15.1** là où le lock dit 4.14.2. La propriété sur laquelle
B-3 repose — un `CapacityLimiter` distinct fait **créer** des fils
supplémentaires plutôt que d'en emprunter à un pool global borné — est une
propriété de l'**implémentation** d'AnyIO, stable depuis la 3.x et documentée,
mais que rien dans ce dépôt ne fige.

**Réserve, pas trouvaille** : le comportement du `CapacityLimiter` est un
contrat public d'AnyIO. Le geste qui la lèverait : épingler `anyio` dans
`requirements.txt`, ou faire installer la CI depuis `uv.lock`.

## R-2 — un chemin prend le singleton hors de la borne, mais il est inatteignable en service

REPAR-13 affirme : « **Rien ne prend le verrou de chargement avant la borne**,
donc aucune inversion n'est possible ». J'ai cherché le contre-exemple plutôt
que de lire la phrase. Les trois chemins vers `_SingletonVerrouille.__call__` :

| site | sous la borne ? |
|---|---|
| `retriever.py:1450` (`_dense_search`) | OK |
| `retriever.py:1577` (`rerank`) | OK |
| **`retriever.py:673`** (`_peripherique_si_charge`, sur le chemin de `/health`) | NON **hors borne** |

Ce troisième est gardé par `if accesseur.cache_info().currsize == 0: return None`
juste au-dessus. Il reste une fenêtre entre ce test et l'appel : si un
`cache_clear()` concurrent passait, `/health` **chargerait un modèle** hors
borne, en tenant le verrou. Mesuré :

```bash
grep -rn "_get_embedding_model.cache_clear\|_get_rerank_model.cache_clear" src/ scripts/
#   -> AUCUN appel en production (24 sites, tous dans tests/)
```

**Atteignabilité nulle en service.** Et il n'y a pas d'interblocage possible : un
fil qui tient le verrou l'a pris **après** la borne, il ne la redemande pas.
L'affirmation est donc **vraie**, mais pour une raison que le commentaire ne
donne pas : ce n'est pas qu'aucun chemin hors borne n'existe, c'est que le seul
qui existe est gardé par un test que rien ne fait échouer en production.
**Réserve.**

Corollaire vérifié : `/health` ne peut jamais **attendre** le verrou de
chargement — si `currsize == 0` il rend `None` immédiatement, si `currsize > 0`
la première lecture de `__call__` sort hors verrou. La route de santé reste
libre pendant un chargement, et c'est bien fait.
